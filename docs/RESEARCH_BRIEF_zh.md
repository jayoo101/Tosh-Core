## 摘要

Tosh 是一个**完全以 BEM 计价**的公平发射平台。当前结算链是 BNB Smart Chain，
计价资产是 BEM（8 位小数 ERC-20，`0x5ce0…695a`），AMM 是 PancakeSwap Infinity。
BNB 只付 gas。三个结构性差异是这个项目的全部论点：

**第一，每个项目拥有一个专属的 PancakeSwap Infinity Hook 合约作为发射引擎。** 这不是
"在曲线里交易、毕业后才建池"的 pump.fun 模式——Infinity 真池在募资结束的那一刻就创建，
而分级货架（Phase 2）是与池**并行运行**的一级发行通道，并且反过来受池子自己的价格约束。

**第二，团队没有预挖。** 发射只铸造 840 万枚创世块；剩余 1,260 万枚随货架逐笔售出
时按需铸造。区块浏览器上不会出现一个持有 100% 供应量的地址。

**第三，平台金库是一个单向阀。** `ToshLadderTreasury` 没有 `withdraw`、`sweep`、
`rescue`，也没有 `delegatecall`；它唯一的对外支出路径 `_buyAndBurn` 的收款地址被
硬编码为 `0xdead`。平台所有者可以调参、可以暂停、可以拉黑，但**无法转移任何人的一
个 wei**。

## 一、它解决什么问题

设计动机直接写在源码注释里（`src/ToshLaunchpadHook.sol`、`src/ToshFactory.sol`）。
用产品语言重述为七条：

**1｜参与前必须先买平台币。** 这既是入场摩擦，也让所有参与者暴露在平台币运营方的
风险之下。Tosh 的做法是端到端同一种计价资产：创世存款、货架铸造、回购弹药、退款，
全部是 BEM。工厂、hook 实现和金库把同一个 `quoteAsset` 焊成 immutable，没有 setter。
这是第二次改价：先从 ETH 换成 BNB（×3.5），再按实测约 26.51 BEM/BNB 换成 BEM。

两处例外，都是刻意的。**PoG 门槛留在 ETH**，因为它量的是以太坊系链上烧掉的 gas。
**发射费留在原生 BNB**（0.005，作为 `msg.value`）：它是创建者遇到的第一笔支出，
要求对方先持有 BEM、再签一次 approve 才能开项目，等于把门槛加在了错误的位置。代价是
它不再是回购弹药，且必须转入 `platformTreasury`——金库只花 BEM 也没有 `receive()`。

**2｜团队持有大额预挖。** 按需铸造解决这一条：`launch()` 只铸创世的 840 万枚，剩下
1,260 万枚在货架被买走时才逐笔铸出。

**3｜团队从曲线便宜的一端铸币再砸回池子，抽干创世资金。** 三层价格闸门：同区块铸造
禁令、`min(现价, TWAP)` 参考价、105% 上限。并且 Phase 2 在**发射当块完全关闭**——由
`launch()` 自己盖上 `lastSwapBlock` 实现，而不是靠边界算术。

**4｜创世参与者在池子打开的瞬间就浮亏。** 55:45 的创世供应拆分在算术上产生**恰好
10%** 的开盘账面溢价，货架 0 再叠 5%，合计 15.5%。推导见第三节。

**5｜池子被永久锁死，散户不敢也无法做 LP，池费累积在一个没人能领的仓位里。** v5.0
不注册 `beforeRemoveLiquidity` 权限位，散户 LP 自由进出；创世仓位的锁定是结构性的
——Infinity 与 V4 一样把仓位归属于创建者，它属于这个 Hook，而这个 Hook 没有任何移除
流动性的代码路径。锁定来自"所有权 + 不存在移除路径"，不来自一个可以被改掉的回调。

**6｜通缩依赖链下机器人收割，有 MEV 风险和运维成本。** 搭便车回购：Tosh 池上一笔交易
的 `afterSwap` 在**有余量 gas 时**顺手买一小片并烧到 `0xdead`。无链下组件。代价是不再
保证每笔交易都带一次回购，兜底是无需许可的 `pokeBuyback()`。

**7｜平台金库可被所有者抽干。** 单向阀，见摘要。

## 二、机制：三段式生命周期

```
Phase 1 · 创世募资          Phase 2 · 池 + 货架并行            Phase 3 · 通缩飞轮
─────────────────          ──────────────────────            ─────────────────
deposit (BEM)              Infinity 真池即刻创建               买入 1% BEM 税
  ├ 10% 返佣碑开          ├ 90% 创世 BEM 全区间注入            ├ 70bps → 金库
  └ 90% → lpQuote           │  + 3.78M 代币，永久锁定             └ 30bps → 平台
                          └ 4000 层货架并行发售                卖出 1% 代币 → 0xdead
时间到 → launch()          受 min(现价,TWAP)×105% 反向约束      金库 → 买回并烧毁
7 天未 launch → 100%       货架收入 99% 归项目方，1% 进金库
无罚金退款
```

### Phase 1 · 创世募资

创建者付 0.005 BNB 发射费，并选择三种募资时长之一：`DURATION_FAST` 3 小时、
`DURATION_STANDARD` 24 小时、`DURATION_SLOW` 72 小时。

**没有募资目标。** `defaultSoftCap`（源码默认 928.4 BEM）还在，但它现在只剩一个作用：
作为 hook 克隆体的 immutable 参数参与决定 CREATE2 地址。没有任何代码读它的数值——
`launch()` 不查，`canRefund()` 不查，存款不在它那里停，远未触及它的募集照常发射。
前端已把它连同进度条、百分比、"募资目标 / 最低募集额 / 超募"等全部措辞一并撤下，
只保留"已筹金额 + 剩余时间"。

它的下限 `MIN_SOFT_CAP_PROD` = 100 BEM 仍然值得看一眼，但要看对理由：这个常数没有
按汇率缩放，因为 8 位小数把阶梯粒度余量从约 1600 万倍塌到了约 4.75 倍。它约束的是
**这个档位本身**能被调到多低，而不是任何一次募资的规模。

`launch()` 真正拒绝的规模只有两种：空募集（无法注入底池），以及小到无法构造单调阶梯的
募集（`RaiseTooSmallForLadder`，实测约 21 BEM）。后者才是真实存在的下限，且远低于软顶。

**下行保护是 100% 无罚金退款：** 仅当 `LAUNCH_WINDOW` = 7 天的僵尸窗口超时（募资结束但
没人调用 `launch()`）。时间一到即可 `launch()`，无论收到多少资金。这意味着"项目方拿了
钱不发射"不是一个能把资金困住的状态。

这一条不只是设计声明：`97` 上的演练项目正是在远低于当时软顶的状态下发射的（募得 0.035
BNB，当时该 hook 冻着的软顶是 0.175 BNB），发射照常完成。见第七节。那次演练跑在 BEM
改造之前的旧工厂上，数字的量纲与今天不同，但它证的那件事——募集额与能否发射无关——
正是软顶后来被整个撤出界面的实证依据。

**每笔存款被抽走 10%（`REFERRAL_BPS` = 1000）作为返佣。** 这 10% 的去向分三种：

- 有项目推荐人：`PROJECT_REFERRAL_SHARE_BPS` = 8000，即这 10% 的 80% —— 也就是存款的
  **8%** —— 归项目推荐人，剩下 **2%** 归终身推荐人。
- 只有终身推荐人：按上述规则结算。
- 无推荐人：进入 `orphanReferral`，在 `launch()` 时**全额转给金库**充当回购弹药。

需要说清的一点：8%/2% 是**同一笔 10% 的内部拆分，不是提高到 10%+**。从池子的视角看，
有没有推荐人都只有 90% 进池——这正是 10% 溢价能成为结构常数而非随返佣率浮动的前提。

### Phase 2 · 池与货架并行

募资结束时 `launch()` 一次性完成：铸造创世块、创建 Infinity CL 池、把 `lpQuote` 与
3.78M 代币全区间注入并永久锁定、盖上同块锁。项目代币地址由 CREATE2 磨到 BEM 之上，
所以 BEM 恒为 `currency0`。

**分级货架不是连续曲线。** v4.x 的 tan(z) 泰勒展开曲线被删除，替换为 4000 个离散定价
的货架：每层 3,150 枚，层间价差 +0.19025%（`TIER_STEP_E18` = 1_001_902_508_266_805_824），
端到端跨度 2000×。价格用快速幂闭式求值，而不是 4000 次连乘——避免 4000 轮截断漂移。
单笔最多跨 `MAX_TIERS_PER_TX` = 32 层。

**货架被池子的价格反向约束。** 门槛条件是 `shelfP0 × STEP^i ≤ REF × 1.05`，其中 REF 是
`min(现价, TWAP)`。而 `SHELF_PREMIUM_BPS` 与 `PRICE_CEILING_BPS` **被刻意设为相同的
10500**，于是两侧的 1.05 相互抵消，条件塌缩为一个不含魔数的比较。这是一处值得注意的
设计：两个常量相等不是巧合，改动其中任何一个都会让条件重新长出一个 1.05。

**货架收入 99% 归 `projectAdmin`，1%（`PLATFORM_TAX_BPS`）进金库当回购燃料。**

### Phase 3 · 通缩飞轮

金库的 `TRIGGER_STEP` = 92.8 BEM，每次动用 `max(92.8 BEM, 余额的 10%)`（`SPEND_BPS` =
1000）再除以 `BATCH_SIZE` = 3 分摊支出，每次 poke 走 `LEGS_PER_POKE` = 1 条腿。回购受
`MAX_BUYBACK_SQRT_DEVIATION_BPS` = 1000（10%）的滑点保护。

## 三、代币经济学

### 3.1 供应拆分

| 层次 | 常量 | 数量 | 占 21M |
|---|---|---|---|
| 硬顶 | `MAX_SUPPLY` | 21,000,000 | 100% |
| 创世块 | `GENESIS_SUPPLY` | 8,400,000 | 40% |
| ├ 领取侧 | `GENESIS_CLAIM_SUPPLY` | 4,620,000 | 22%（创世块的 **55%**） |
| └ 池侧 | `GENESIS_LP_SUPPLY` | 3,780,000 | 18%（创世块的 **45%**） |
| 货架 | `BONDING_MAX` | 12,600,000 | 60% |

算术闭合：8,400,000 + 12,600,000 = 21,000,000，恰好等于硬顶。

### 3.2 10% 溢价是怎么来的

```
存款人成本基准  P_raise = R / GENESIS_CLAIM_SUPPLY = R / 4,620,000
池子开盘价      p0      = 0.9R / GENESIS_LP_SUPPLY = 0.9R / 3,780,000

p0 / P_raise = (0.9 / 1.89) × 2.31 = 1.10   （精确值）
```

**这个 1.10 由三个数共同决定：55、45、以及 10% 的返佣率。** 动其中任何一个，溢价就变。
货架 0 定在 `p0 × 1.05`，所以相对成本基准是 1.155。

值得强调的是：这不是一个被写死的目标价，而是三个独立参数的算术后果。测试
`test_genesisPremium_isExactlyTenPercent` 钉的是这个**关系**（`assertApproxEqRel`），
而不是一个硬编码价格——所以任何人改动 55/45 或返佣率，测试会在这里失败而不是默默发布
一个不同的溢价。

这一段与计价资产无关：它全部是比值，所以从 ETH 换到 BNB 不改变其中任何一个数字。

### 3.3 40/60 拆分：抑制早期通胀的主旋钮，以及它没解决的问题

等大货架在市价 `R×` 时释放 Phase-2 的 `log(R)/log(SPAN)` **比例**，而这个比例只取决于
跨度、与 Phase-2 有多大无关。所以要减少上涨途中砸向市场的**绝对代币数**，唯一的办法
是缩小 Phase-2 本身、把差额交给创世块——那部分供应在发射时已经定价、已经在流通，不构成
新增卖压。三代配置在 2× 点的对比：

| 配置 | 2× 时释放 | 占 `GENESIS_SUPPLY` |
|---|---|---|
| 20/80 + 1000× 跨度 | 1,688,400 | 40.2% |
| 20/80 + 2000× 跨度 | 1,533,000 | 36.5% |
| **40/60 + 2000× 跨度（当前）** | **1,149,750** | **13.7%** |

**但要留意那个分母。** `GENESIS_SUPPLY` 是 8.4M，其中 **3.78M 被永久封在创世 LP 仓位
里**——存在但永不流通。换成真实可流通量：

| 分母 | 代币 | 占比 |
|---|---|---|
| `GENESIS_SUPPLY`（含锁定 LP） | 1,149,750 | 13.7% |
| 4.62M 领取流通量（真正会交易的部分） | 1,149,750 | **24.9%** |
| 释放后总流通（4.62M + 1.15M） | 1,149,750 | **19.9%** |

所以 40/60 相对 20/80 是实质改进（36.5% → 13.7% 是同基准对比），但在两倍价位上市场仍需
消化**约五分之一到四分之一的活跃流通量**。如果 ~10% 是硬目标，跨度或拆分还得再动——这是
尚未关闭的决策 D1。

我把这段完整保留在研报里，是因为它是这个项目文档风格的代表：一个对自己有利的数字
（13.7%）旁边，紧挨着写清它的分母有问题，以及换成诚实分母之后是多少。

### 3.4 费用结构

| 收费点 | 费率 | 去向 |
|---|---|---|
| 池费 | 0.30% | 第三方 LP（含散户），由 Infinity CL 原生结算 |
| 换手税·买入 | 1.00% BEM | 70bps → 金库（回购燃料）；30bps → 平台维护收入 |
| 换手税·卖出 | 1.00% 代币 | **全额** → `0xdead`，就地烧毁，平台不分成 |
| 货架分成 | 1% BEM | → 金库；99% → `projectAdmin` |
| 发射费 | 0.005 **BNB**（原生） | → `platformTreasury`，**不进金库** |
| 孤儿返佣 | 存款的 10% | → 金库 |

交易者的总摩擦是 **1.30%**。

**一处必须说明的信任让步。** v5.0 原本的表述是"四条管道全部流入金库，唯一允许的用途
是买回并烧毁"。这句话现在是假的：买入侧 1% 税中的 30bps（`PLATFORM_SWAP_FEE_BPS`）
归平台，不回购、不烧毁，是平台可自由支配的收入。到达回购引擎的绝对金额没变（仍是买入的
70bps），变的是交易者总摩擦从 1.00% 上升到 1.30%——多出的 30bps 是新增的，不是从回购
里挪出来的。

源码把这件事当成需要被看见的事写：`PLATFORM_SWAP_FEE_BPS` 的注释里明确写着"这是与
v5.0 声称的『全部承诺用于买回销毁』的一次刻意背离"。并且收款地址
`platformFeeRecipient` 被设为 **immutable**——这是对审计发现 M-2 的回应：v4.x 允许工厂
所有者重定向 Phase-2 的费用路由，现在不允许了。

**但 immutable 这次也反咬了一口。** 同样的不可变性意味着一个被写错或被泄露的收款地址
同样无法纠正，而这正是测试网 `97` 现在的处境，见第五节。

另外提醒一个阅读陷阱，源码本身也警告过：`TAX_BPS` = 100 与 `PLATFORM_TAX_BPS` = 100
数值相同、相隔三十行，但基数完全不同——前者是**换手输入**的 1%，后者是**货架收入**的
1%。两者永不作用于同一个 wei（货架铸造不碰池子）。

## 四、技术架构

### 4.1 四个合约的职责边界

| 合约 | 数量 | 职责 |
|---|---|---|
| `ToshFactory` | 每链一个 | `createLaunch`（CREATE2）、`registerPoG`、创世存款网关、返佣图、黑名单/冷却/暂停 |
| `ToshLadderTreasury` | 每链一个 | 四条管道的收款、回购策展、`autoPiggybackBuyback`、`pokeBuyback`、`_buyAndBurn` → `0xdead` |
| `ToshLaunchpadHook` | **每项目一个** | Phase 1 存款/退款/发射；Phase 2 货架铸造/领取；Infinity CL 回调 |
| `ToshToken` | 每项目一个 | ERC-20，硬顶 21M，按需铸造 |

Hook 通过 CREATE2 部署为 EIP-1167 极简代理克隆（运行时 121 字节，initcode 131 字节），
所以"每个项目一个专属 Hook"在 gas 上是可行的。规则在部署时冻结为 immutable。

**一处因迁移而消失的复杂度。** Uniswap V4 把 Hook 的权限编码在**地址的低位**里，因此
每次部署都要挖一个满足掩码的 CREATE2 salt。Infinity 改为让 Hook 自己用
`getHooksRegistrationBitmap()` 声明一个 uint16 位图，地址不再承载语义。于是整个地址
挖矿器——链上的 bits 闸门、链下的 salt 搜索、以及教人挖矿的部署文档——被整体删除，而
不是被移植。这是本次迁移**唯一一处让系统变简单**的改动。

### 4.2 为什么是 BNB Smart Chain + PancakeSwap Infinity

本节替换 2026-09-13 版的"为什么选 Robinhood Chain"。那套 `4663` 部署已整体退役，且
**不迁移任何东西**——旧工厂上的项目、PoG 证明、金库余额都留在原处。

**为什么换 AMM，不只是换路由器。** PancakeSwap v2 和 v3 **完全没有 hook 机制**。而这
个协议本身就是一个 hook：货架定价跑在 `beforeSwap`，70bps 税和金库搭便车回购跑在
`afterSwap`，同块锁是 hook 状态。在 v2/v3 上这些逻辑无处安放。所以唯一的选项是
**PancakeSwap Infinity**，即 PancakeSwap 支持 hook 的 AMM（据其开发者文档，2025 年
3 月完成审计）。

**真正的决定因素是测试网，不是流动性。** 用 `cast code` 实测（2026-09-17）：

| 合约 | BSC 主网 `56` | BSC 测试网 `97` |
|---|---|---|
| Infinity `Vault` | 8,347 B | 8,347 B |
| Infinity `CLPoolManager` | 20,885 B | 20,886 B |
| Infinity `CLPositionManager` | 24,004 B | 24,004 B |
| Uniswap V4 `PoolManager` | 24,009 B | **无代码** |
| Uniswap V4 `PositionManager` | 23,877 B | **无代码** |

Uniswap V4 在 BSC 主网是部署了的，但**测试网 `97` 上没有**。选 V4 就等于没有真测试网，
只能对着 fork 演练；选 Infinity 则两条链都有。第七节记录的那次完整演练——以及它抓出来
的两个真 bug——是这个选择直接换来的。

**合约层几乎零改动。** 三条已验证的原因：`_hasArbSys` 在构造时按
`ARB_SYS.code.length != 0` 取值，所以没有该预编译的链自动回落到 `block.number`，而
BSC 的 `block.number` 正是同块锁与 `maxMintable()` 想要的语义；BSC 自 2024-06-20 的
Tycho 硬分叉（BEP-343）起支持 EIP-1153，瞬态存储记账成立；实测出块时间 0.451 秒，
`uint48 _lastSwapBlock` 仍有约 400 万年的余量，同块锁与 TWAP 闸门的粒度有意义。

**计价资产现在是 BEM。** 第 4.2 节上一版写的是"评估过 ERC-20，已否决"。那条决定在
2026-09-19 被推翻，论证与代价写在 `docs/BEM_QUOTE_ASSET.md`。被推翻的那几条理由并
没有消失：BEM 可被其 minter 增发、`97` 上没有测试 BEM、池子从原生币对变成 ERC-20
对。换来的是：存款、货架、回购全部走 `transferFrom`，`currency0` 靠 CREATE2
把项目代币磨到 BEM 之上来保证。

**发射费是唯一走回头路的那一项。** 它跟着改成了 BEM，之后又改回原生 BNB（0.005），
理由见 2.1 节。这也重新引入了一个 ERC-20 时期不存在的风险：`platformTreasury` 若拒收
原生币，`createLaunch` 会被整体砖化。它是一个 Gnosis Safe，能收 BNB，且
`verifyOwnerSafe.mjs` 与 `preflightMainnet.mjs` 在部署前都会验这一条——这是一个被接受
并有前置检查兜底的风险，不是一个被忽略的风险。

**金额标定现在跨了两道汇率，仍然不是预言机。** 先是 ETH→BNB ×3.5，再是 BNB→BEM
按当时现货约 26.51（回购触发 3.5→92.8、PoG 上限 1.75→46.4）。发射费不在其列，它回到
BNB 之后是直接按绝对额定的 0.005，与汇率无关。`MIN_SOFT_CAP_PROD` 也没有跟着缩，从
0.035 BNB 提到 100 BEM，因为 8 位小数会让更小的取值把阶梯 `p0` 算成零。汇率变动不会
自动跟随，需要人工调参。

### 4.3 Proof-of-Gas 配额

创世存款不是无限开放的，配额由 Proof-of-Gas 决定：服务端扫描申领地址在多条链上的
历史 gas 支出，低于门槛的直接拒绝，通过则按汇率算出 `maxAlloc`，先受链下上限约束，
再受链上 `maxPogAllocationLimit()` 约束。

**这条带里有一个刻意的双币种断层，必须讲清楚：**

| 档位 | 当前值 | 币种 | 常量 |
|---|---|---|---|
| 门槛 | 0.025 | **ETH** | `DEFAULT_POG_GAS_FLOOR_WEI` |
| 汇率 | 1 ETH 历史 gas → 46.4 | **BEM** | `DEFAULT_GAS_TO_ALLOC_RATE` |
| 链下上限 | 46.4 | **BEM** | `DEFAULT_POG_MAX_ALLOC_WEI` |
| 链上上限 | 46.4 | **BEM** | `maxPogAllocationLimit`，源码默认与链 `97` 实测一致 |

门槛留在 ETH 是**对的而不是遗漏**：被测量的东西是申领者在以太坊系链上真实烧掉的
gas，那本来就以 ETH 结算，换算成 BNB 只会引入一个没有必要的汇率假设。汇率与上限则
必须是 BEM，因为它们发放的是 BEM 配额。扫描器为此按链携带换算系数，打破了原先
"所有链都是 ETH"的隐含不变量。1 ETH 的历史 gas 仍然恰好填满上限——46.4 / 46.4，
和 ETH 时代的 1.75 / 1.75、BNB 时代的 1.75 / 1.75 是同一个锚。

三者并非独立：扫描器实际停止计数的 gas 上限是 `上限 ÷ 汇率` 推导出来的，因此调高
汇率会同时缩短值得扫描的历史长度，而门槛高于这个推导上限的组合是不自洽的，接口会
拒绝。链下上限也不允许高于链上 `maxPogAllocationLimit()`——否则签出的凭证会让
`registerPoG` 直接 revert；要抬高须先改链上档位。

三项都是所有者可调的链下参数，必须由所有者签名后经 `POST /api/admin/config` 下发；
未被本次签名覆盖的档位以字面量 `keep` 签入，无法夹带修改。

**扫描哪些链，是一个尚未关闭的问题。** 当前扫描表是 Ethereum、Arbitrum、Optimism、
Base 四条必需链，加上 Robinhood `4663` 作为非必需项。**BSC `56` 不在表内**——不是疏忽，
而是扫描走的是 Blockscout 的 keyed API，而 BSC 需要 Etherscan v2 通道，该通道尚未接入。
结果是一个明显的别扭状态：协议搬到了 BSC，但 PoG 仍在读一条已退役的链、不读自己的
结算链。这一条记在第八节风险里。

配额以 EIP-191 签名的形式下发，摘要为
`keccak256(abi.encode(sender, maxAlloc, nonce, deadline, factory, chainId))`，
六个字段全部签入。工厂在 `registerPoG` 里用 `address(this)` 参与哈希，因此一份指向
其他工厂的签名在真工厂处根本无法恢复。

这套机制的作用是把"每个新地址都是一份新配额"的女巫攻击成本，锚定到攻击者在主流链上
真实烧掉的 gas 上——一个无法凭空生成的历史。

**但这条锚曾经可以用时间绕过，这是最近才补上的一个洞。** 上面算的是"一个地址一份
配额"，而配额每 `quotaWindowDuration`（24 小时）刷新一次，被消耗的记录 `nativeDeposited`
却是累计值、不随之清零。冷却时长原本也是 24 小时，两个时钟一同步，同一个钱包就能在
一个 72 小时的创世窗口里领三次配额、分三笔投进**同一个**项目。对刚好卡在门槛上的低保
号，这不是削弱威慑而是反转威慑：100 个号各烧 0.025 ETH（合计 2.5 ETH）本来只能换到
116 BEM，分三次就是 348 BEM，按 92.8 BEM/ETH 折 3.75 ETH——2:1 的威慑变成 1.5:1 的
补贴。

修法是把冷却提到 **72 小时**，即不短于最长的那档创世窗口 `DURATION_SLOW`。于是第二笔
存款的可行时间窗恒为空集：冷却起算不早于项目创建，又至少持续整个窗口，因此它结束时
创世必已关闭。**任何钱包在任何单个项目里的持仓，上界因此是一次配额抽取 $Q(A)$**，而不
是 $Q_{max}$ 在多个窗口上的累加。

⚠ 值得研判者注意的是这条性质的**强度**：它不是不变量，而是"工厂上的可变拨盘 ≥ Hook 上
的常量"，两者分处不同合约、互不引用，72 对 72 没有任何余量。所有者一笔 `setCooldownDuration`
就能废除它，且不 revert、不改变任何界面。合约侧由 `test_cooldown_isAtLeastTheLongestGenesis`
钉住源码默认值，部署侧由监控 `STATE-08` 每小时比对链上实际值（P1，会呼叫）——单元测试
管不到部署后被调的拨盘，这是刻意分成两层的原因。

## 五、信任边界：所有者能做什么，不能做什么

这一节是研报里最该被逐条核对的部分。

**能做：** 调整发射费（原生 BNB，上限 `MAX_LAUNCH_FEE` = 0.5 BNB，允许设为 0）、
默认软顶（上限 `MAX_DEFAULT_SOFT_CAP` = 20,000 BEM，但改它只影响新项目的 CREATE2
地址，不影响任何人的资金）、PoG 配额上限（上限 20,000 BEM）、冷却
时长（上限 `MAX_COOLDOWN` = 7 天）、黑名单、暂停、策展哪些代币进入回购列表、发起阶梯
暂停（上限 `MAX_HALT_DURATION` = 7 天）。

这里面有一条值得单独列出，因为它是这张清单上**唯一行使起来无声无息**的权力：把
`cooldownDuration` 调到 `DURATION_SLOW` 以下，等于废除单项目一次存款的规则，恢复上一节
描述的分期建仓路径。其余多数拨盘行使时都会自己显形——改发射费会出现在下一个发射界面
上，暂停和黑名单会挡下一笔本该成功的交易——而这一个什么都不 revert、只发一条
常规的 `CooldownDurationUpdated`，所有界面照旧。对应的补偿控制是监控 `STATE-08` 直接读
链上状态而非只听事件（事件分不清调高与调低）。这是一个自觉的取舍：把规则留作可调的
市场参数，代价是它不具备不变量的强度。

**不能做：**

- **不能动任何人的钱。** 金库无 `withdraw`/`sweep`/`rescue`/`delegatecall`，唯一出金
  路径的收款方硬编码为 `0xdead`。
- **不能改平台费收款地址。** `platformFeeRecipient` 是 immutable。
- **不能移除创世流动性。** Hook 没有该代码路径。
- **不能用暂停扣住退款或收益。** 有两个专门的测试守这条：
  `test_ladderHalt_cannotHoldAnUnderCapGenesisHostage` 和
  `test_ladderHalt_blocksNeitherLaunchNorPayouts`。

### 5.1 治理现状：本文最严重的一条负面事实

2026-09-13 版在这里写的是"3/N Gnosis Safe `0x2953…e27A`，工厂与金库均已
`acceptOwnership()`"。**那句话描述的是已退役的 `4663`，在 BSC 上一个字都不成立。**

测试网 `97` 上的真实读数（2026-09-18）：

```
工厂 owner()              → 0x73db078fa94607893270079AC8F5c7492aB480cd
工厂 pogSigner()          → 0x73db078fa94607893270079AC8F5c7492aB480cd
工厂 platformTreasury()   → 0x73db078fa94607893270079AC8F5c7492aB480cd
金库 owner()              → 0x73db078fa94607893270079AC8F5c7492aB480cd
```

四个角色是**同一个外部地址**，不是多签。更糟的是：**这个地址的私钥曾被提交进公开
仓库并推送。** 泄露的脚本已删除，但删除不撤销泄露——任何克隆过该仓库的人都能以这四
个身份签名。而 `platformTreasury` 是 `immutable`，所以 `97` 无法通过轮换密钥修复，
只能重新部署。

该部署是测试网、不持有价值，故意保留在原地以便本文的地址仍可解析。**主网 `56` 因此
有了一个硬前置条件：必须用从未在本仓库出现过的全新密钥部署，并且四个角色必须拆开**
——单一地址持有全部角色意味着一次泄露即终局，而其中 `platformTreasury` 事后不可改。
截至本文撰写时，`0x73db…80cd` 在 `56` 上 nonce 为 0、余额为 0，从未交易过。

## 六、验证与安全姿态

**先说迁移损失了什么。** `4663` 那套部署有两项本节曾经最硬的证据：五个合约在
Blockscout 与 Sourcify 上的独立验证，以及一个把部署固定到源码的带注解 tag
`deploy-4663-2026-09-12`。**这两项在 BSC 版本上目前都不存在**，因为 `56` 尚无部署，
且 BSC 的验证走 Etherscan v2 而非 Blockscout，需要一把项目尚未持有的 API key。这是
迁移的直接代价，本节不绕开它。

**仍然成立、并且更强了的部分：**

**测试：** 389 通过、4 跳过，普通模式与 `--isolate` 各跑一次，两者都是 CI 门禁。套件
包含有状态不变量测试。那 4 个跳过项检查的是 `56` 部署，在有部署之前保持休眠。向
Infinity 的移植包含在这个数字里，并且移植过程本身抓出两个真 bug：结算款项被付给了
pool manager 而不是 `Vault`，以及金库回调仍在鉴权 manager。

**部署可复现性：** initcode 哈希仍由 `RecomputeInitcodeHash` 对着本仓库复核，任何人
都能从链上和源码两侧独立算出同一个值而不必信任任何人。缺的只是把它钉到某次 BSC
部署的 tag。

**真测试网演练：** 完整生命周期已在 `97` 上对真实 Infinity 部署跑通，而非仅对 fork。
证据价值见第七节。

**链下监控：** `monitoring/watch.mjs` 巡检链上状态并分级告警（P0/P1），包含一项
WATCHER-03 检查——状态文件记录的 chainId 与端点实际返回的 chainId 不一致时报警并重置
检查点，专门防"切换主网后监控还盯着旧链"。这项检查在本次换链中正是它自己设计要应对
的场景。

**一个有代表性的案例。** 2026-09-12 重新部署工厂之后，公开状态页有四天时间一直在读**已
退役**的旧工厂的 `paused()`。这意味着如果那四天里发生事故并暂停了真工厂，状态页会继续
显示"运行正常"——恰好是它存在的目的的反面。原因是既有的漂移检查会用四个文本字段投票
"测试网还是主网"，而一个退役的主网工厂投的是"主网"；缺失的区分是**哪一个**主网工厂，
而在这个月之前主网上只有一个。修复之后新增了检查 6b，并且用"让它失败"的方式验证过。

把这件事写进研报，是因为它比任何"我们很重视安全"的表述都更能说明这个项目的实际工程
姿态：缺陷被记录、被归类、并且补上的检查会被验证到真的会响。第五节那条私钥泄露按
同样的规则处理——写进来，而不是删掉脚本就当没发生。

### 7.1 `97` 演练：本文最强的正面证据

截至 2026-09-18，已在测试网 `97` 上对**真实的 PancakeSwap Infinity 部署**（而非 fork）
完整跑通全部阶段，每一步都是独立的链上交易：

| 阶段 | 结果 |
|---|---|
| Phase 1 创世 | 入金 0.035 BNB，hook `0x46e8…393f` |
| Phase 2 发射 | 区块 131601100，**募集额仅为该 hook 软顶的 1/5 仍成功**（0.035 / 0.175 BNB）——软顶后来被整个撤出界面的实证 |
| Phase 2b 挂牌 | `ladderTokenCount` = 1 |
| Phase 3 买入 | 0.002 BNB 换得 222,607 枚 |
| Phase 4 阶梯铸造 | 945 枚，报价与实收**逐 wei 一致** |

**它证明了 fork 测试证明不了的东西。** 最有说服力的一条是它推翻了一个原本写错的流程：
挂牌 `addLadderToken` 原本和 `launch()` 写在同一笔交易里，而这在任何时候都不可能成功
——`addLadderToken` 要读 TWAP，而 `launch()` 刚把两个预言机检查点都盖成当前时间戳，
`span` 为 0，getter 返回 0，金库直接 `TwapNotMature()` 拒绝。这个错误在仿真阶段就被
拦下，从未真正发消息上链，修复方式是把挂牌拆成独立阶段、在 `TWAP_WINDOW`（1800 秒）
之后执行。

一个可被任何人复核的旁证：演练代币 `RHRSL`
（`0xb3b9443a717138aFB542156D27279726BAFf5A63`）的 `totalSupply()` 读出来是
**8,400,945**，而不是整数的 `GENESIS_SUPPLY` = 8,400,000。多出的 945 枚正是 Phase 4
阶梯铸造的量——总供应量本身就是回购腿在真链上运行过的证据。

### 7.2 仍未被验证的部分

**主网零运行记录。** `56` 无部署，因此主网上线项目数为 0、金库余额为 0。

**用户路径仍未走通。** `97` 的演练由 `RehearseTestnet.s.sol` 脚本驱动、PoG 由本地
签发，走的不是用户会走的 UI/API 路径。已完成自动化实测的是鉴权、预言机密钥加载、
多链 gas 扫描与链上 nonce 读取；尚未走通的是配额签发之后的 `registerPoG` 与创世存款
——这两步需要一个有真实 gas 历史且有余额的钱包。

**运维侧尚未就位。** 治理多签未建立（第五节）、BSC 验证 API key 未持有（第六节）、
带 key 的 BSC RPC 未接入（当前用公共 dataseed，监控会被限流）、PoG 扫描表未纳入 `56`
（第 4.3 节）。

## 八、风险

**1｜主网零运行记录，且尚未部署。** 见第七节。任何"机制如此设计"的陈述都不等于
"机制在真实对抗环境下如此表现"。`97` 的演练缩小了这个差距但没有消除它。

**2｜测试网密钥已泄露，且部分角色不可修复。** 见第 5.1 节。这是本文最严重的一条。
它不影响主网（`56` 无部署，该地址在 `56` 上从未交易），但它意味着 `97` 上的任何读数
都不能被当作"受控系统"的读数，并且它把"主网必须换全新密钥"从建议变成了前置条件。

**3｜早期释放比例仍高于理想值。** 2× 价位释放约 20%–25% 的活跃流通量（第 3.3 节），
列为未关闭的决策 D1。

**4｜搭便车回购不保证发生。** 它依赖每笔交易的 gas 余量（`PIGGYBACK_MIN_GAS` =
270,000，该值在移植后按 Infinity 的实测 gas 地板上调过）。兜底是无需许可的
`pokeBuyback()`，但这意味着在无人 poke 且交易都很拮据的情况下，通缩推进会变慢。

**5｜平台确实拿走 30bps。** 见第 3.4 节。这是对"全部用于回购销毁"叙事的一次真实
削弱，本文按源码的方式如实列出而非淡化。

**6｜BSC 上没有任何字节码验证。** 不是"partial match 而非 exact"的程度问题，而是
彻底没有：`56` 无部署，`97` 未验证，缺一把 Etherscan v2 API key。严格的读者在
`56` 完成验证之前，只能对着源码而不是对着链上字节码做判断。

**7｜依赖 BNB Smart Chain 与 PancakeSwap Infinity。** 单链部署，继承该链的活跃度与
去中心化程度。AMM 侧的依赖是新的：Infinity 于 2025 年 3 月审计，本协议对它的适配
只有约一周的历史，其中两个已知 bug 是在移植过程中才发现的（第六节）。

**8｜金额标定是一次性拍定的，不是预言机。** 现在跨 ETH→BNB→BEM 两道汇率（第 4.2
节）。BEM/BNB 比 BNB/ETH 浅得多：档位拍定时 BEM 池深度约 74 WBNB，两日内供应 +4.81%、
对 BNB 跌了 24%。汇率显著变动时，PoG 上限、回购触发额、软顶下限的真实经济含义会漂移，
需要人工调参而不会自动跟随。发射费不受这条影响——它以原生 BNB 计价，只跟 BNB 走。

**9｜PoG 扫描表与结算链不一致。** 仍在扫 Robinhood `4663`、不扫 BSC `56`
（第 4.3 节）。这不构成安全漏洞，但它意味着 PoG 当前测量不到申领者在本协议自己的
结算链上的活动。

**10｜PoG 依赖链下服务。** gas 扫描走 Blockscout 的 keyed API，有日额度上限
（`CREDIT_RESERVE` = 2000 时拒绝新扫描）。额度耗尽会导致创世申领对所有人关闭——代码
把这一条明确写为"我们自己交付给自己的拒绝服务"，并为此设了三层预算闸门。

**11｜治理不为零。** 所有者的权限边界见第五节。主网上它还将是一个多签而非无治理。
